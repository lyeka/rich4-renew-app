# 游戏 Agent 开发 Roadmap

技术底座：Google ADK Go。更新日期：2026-11-09。

本文确定 Agent 玩家的实现方案、开发顺序、阶段交付物和验收标准。无界面运行、动画与规则分离、UI 中的操作限制、多步操作和小游戏均纳入正式开发范围。

本文是设计与开发计划。当前阶段 1 已完成，交付与验证记录见 [阶段 1 验收记录](agent-stage1.md)；其余阶段仍待实现。

## 一、项目目标与实现原则

在现有游戏中增加一个由 Google ADK Go 驱动的 Agent 玩家：

- 与真人具有相同的信息权限和合法操作能力。
- 自主查询信息、选择行动、处理其他玩家事件。
- 支持完整对局、多步操作和长上下文。
- 接入 OpenAI、OpenRouter、DeepSeek，通过配置选择已验证的模型。
- 浏览器正常游玩与无界面评测使用相同的游戏规则和玩家接口。

**游戏规则、输入校验和流程推进由确定性代码执行；策略选择由模型完成。** 不编写“现金达到多少就买地”之类规则来替代模型决策，也不在模型失败时悄悄切换为现有电脑玩家。

运行失败时，允许有限重试；超过预算后，按游戏已有的超时规则处理。没有默认处理规则的决策进入暂停状态，保留恢复入口。

## 二、确定后的整体设计

| 部分 | 承担职责 |
|---|---|
| **TS 游戏宿主** | 驱动游戏、管理当前决策、执行规则、产生随机结果、记录事件 |
| **玩家接口** | 提供可见信息、合法操作和查询；校验输入并交给游戏逻辑 |
| **Go Agent 服务** | 管理运行、组织上下文、通过 ADK 调用模型和工具 |
| **Session** | 保存该局该座位的交互记录、计划和摘要 |
| **评测运行器** | 无界面运行同一套游戏，记录结果、成本和失败情况 |

采用**单 Agent、自主工具调用、按游戏决策触发运行**的方式。暂不引入多 Agent 协作和跨局经验库。

每局、每个 Agent 座位使用一个 Session，但每次决策重新构建有限上下文，不将整局历史自动全部发给模型。

## 三、现有项目接入问题的实现方案

| 问题 | 确定的实现方案 |
|---|---|
| 无界面模拟器目前主要支持托管 AI | 抽取共享异步游戏驱动，浏览器和无界面运行器都通过控制器接口提供输入 |
| 动画开关影响小游戏结算 | 将交互游戏逻辑与绘制分离，关闭动画只影响表现，不能切换奖励计算方式 |
| 操作限制存在于 UI 中 | 抽取共享的操作资格和目标筛选逻辑，UI 与 Agent 调用同一实现 |
| 目标选择依赖视野 | 将视野作为明确的交互状态；允许查看、移动视角和选择目标的范围遵循原有规则 |
| 小游戏接口接受最终分数 | 对 Agent 开放实际控制输入，由小游戏状态机计算得分，禁止直接提交分数 |
| 转盘等接口接受停止帧 | 对 Agent 提供开始、观察、停止等合法控制，由游戏宿主记录实际发生时刻并计算结果 |
| 道具使用需要多次选择 | 每个待回答问题有独立决策 ID，同一次操作用共同操作 ID 关联 |
| 其他玩家行动分散在不同路径 | 从共享游戏驱动采集事件，整理为结构化业务事件，再按座位过滤 |

对于有实时限制的小游戏，Agent 的模型调用耗时计入实际交互时间。无界面运行也遵守相同时间规则；加速只能作用于不影响决策机会和结果的表现环节。

这部分不要求模型每帧操作。工具可以表达“移动到当前位置”“按住某方向一段时间”等合法输入，但不能自动替模型搜索最优目标或读取未来状态。

## 四、开发 Roadmap

### 阶段 1：建立工程基础与协议

**状态：已完成（2026-11-09）。** [协议](../contracts/README.md)、[Go 基础](../agent-service/README.md)、[无素材夹具](../eval/README.md)。这里完成的是契约和测试入口，游戏接入仍在后续阶段。

**重点：先固定两端契约、决策边界和成功条件。**

主要工作：

- 建立 `agent-service/`、`contracts/`、`eval/` 的基础结构。
- 整理全部决策类型和玩家可见信息。
- 定义普通决策、连续交互、多步操作之间的关系。
- 定义快照、事件增量、查询、输入提交、执行结果和取消消息。
- 明确回答已消费与业务效果已发生的区别。
- 定义请求去重、事件顺序、版本和恢复语义。
- 固定 ADK 版本，建立模型适配测试入口。
- 准备可运行地图及不依赖外部素材的核心测试夹具。

**交付物：**协议 Schema、生命周期说明、典型交互样例、项目启动结构。

**验收标准：**所有可达决策均有协议表达；多步操作、实时交互和异常流程没有语义缺口。

### 阶段 2：建立统一游戏宿主和玩家接口

**重点：让任何控制来源都能通过同一套合法输入驱动游戏。**

主要工作：

- 抽取共享异步驱动，统一管理引擎推进、待决策问题和输入消费。
- 分离控制来源与真人身份、托管状态等原有概念。
- 实现玩家视图、信息查询和合法操作描述。
- 抽取 UI 中的权限和目标选择限制。
- 接入小游戏状态机，将输入、时钟、随机数和结果计算归游戏宿主管理。
- 分离表现事件和业务事件，建立按座位过滤的事件流。
- 让浏览器和无界面入口共享上述实现。

**交付物：**共享游戏驱动、玩家接口、交互适配器、可见事件流。

**验收标准：**

- 相同初始状态、随机源和带时间的合法输入序列，在两种运行方式下产生相同业务结果。
- 关闭动画不改变规则和奖励。
- 查询不能改变状态或推进随机数。
- Agent 接口无法绕过真人受到的操作限制。

这里使用录制输入和测试场景验证规则一致性，不用固定策略替代最终 Agent。

### 阶段 3：打通 WebSocket 与决策生命周期

**重点：建立可靠的跨进程控制通道。**

主要工作：

- 游戏端主动连接 Go 服务，绑定对局和座位。
- 实现决策通知、事件传递、查询、行动提交和结果返回。
- 支持普通一次性回答和小游戏连续控制输入。
- 实现请求关联、过期检查、去重和执行状态查询。
- 保证等待工具结果时，连接仍能处理返回消息。
- 游戏端统一仲裁决策结束和超时。
- Go 按座位串行运行，避免新旧决策同时修改同一个 Session。

**交付物：**通信模块、协议集成测试、连接状态管理。

**验收标准：**普通、多步和连续交互均可跨进程完成；重复消息、迟到回答和结果丢失不会造成重复操作。

### 阶段 4：接入 ADK 和完整游戏工具

**重点：让模型真正负责选择行动。**

主要工作：

- 实现模型创建与适配层，统一向 ADK 提供模型接口。
- 接入目标服务的工具调用、流式返回、取消和使用量统计。
- 对提供商特有的推理字段和续接要求进行适配及测试。
- 配置 Runner、LLMAgent 和按对局、座位隔离的 Session。
- 实现局面查询、规则查询、目标查询、决策提交和实时控制工具。
- 根据当前交互阶段提供相关工具与参数约束。
- 设置调用预算，处理参数错误、工具失败和模型未提交行动等情况。
- 用游戏端结果决定本次决策是否完成。

第一条模型闭环先覆盖购买和多步道具操作，随后补齐阶段 1 中列出的全部决策类型。每增加一类，就同步增加集成场景。

**交付物：**能够覆盖完整玩法的 ADK Agent。

**验收标准：**

- 模型可以自行选择查询、处理工具结果并完成操作。
- 不依赖规则 AI 代替策略选择。
- 各目标模型通过多轮工具调用测试。
- 小游戏得分、骰子点数和结算由游戏逻辑产生。

### 阶段 5：实现长对局上下文与局内计划

**重点：对局变长时，信息仍准确，输入仍可控。**

每次决策构建：

```text
必要规则与工具
+ 当前玩家可见快照
+ 尚未处理的相关事件
+ 有效计划与历史摘要
+ 本次运行的工具交互
```

主要工作：

- 当前事实每次刷新，避免旧快照重复进入模型输入。
- 其他玩家事件持续记录，在需要决策时批量提供。
- 通过事件 ID 和游标防止重复处理或遗漏。
- 为事件、查询结果、计划和摘要分别设置预算。
- 在 Session State 中维护目标、依据和复查条件。
- 对旧事件进行摘要或结构化汇总，保留原始记录供查询和排查。
- 当前运行保留完整的工具调用关联。
- 验证长对局中的 Session 读取和存储开销，避免只控制模型 Token、却让服务端处理成本持续增长。

**交付物：**上下文构建、事件处理、计划管理和摘要机制。

**验收标准：**长对局输入保持在预算内；最新事实不会被旧摘要覆盖；计划能够随局势更新；历史记录可追溯。

### 阶段 6：完成运行可靠性、持久化和用户体验

**重点：让完整对局成为稳定功能。**

主要工作：

- 展示 Agent 正在查询、决策、执行或等待恢复的状态。
- 实现单次决策与整局的时间、调用次数和费用预算。
- 区分可重试错误、决策失效和执行结果未知。
- 保存 Session、计划、决策元数据和执行记录。
- 支持连接中断后的状态核对和继续运行。
- 基于现有回合存档提供明确的保存／加载边界，并关联相应的 Agent 状态。
- 确保加载旧存档不会继续使用来自后续局面的计划和历史。
- 对无法继续的情况提供明确暂停和恢复入口。

**交付物：**稳定运行、存档关联、故障处理和基础交互界面。

**验收标准：**长对局、掉线、模型故障、保存和加载均有明确行为；不存在静默切换规则 AI 或重复执行。

任意指令位置的崩溃恢复不作为首版承诺，首版恢复边界与游戏支持的存档边界一致。

### 阶段 7：系统评测与交付

**重点：验证 Agent 的效果、成本和完整性。**

测试从前面各阶段持续建设，这里完成批量运行和对照实验。

评测覆盖：

| 维度 | 核心指标 |
|---|---|
| **信息与操作权限** | 隐藏信息隔离、非法输入拒绝、查询无副作用 |
| **执行可靠性** | 对局完成率、工具失败率、重复执行、暂停与恢复 |
| **决策质量** | 胜率、资产表现、典型策略失误 |
| **上下文质量** | 过时信息使用、事件遗漏、计划失效、压缩损失 |
| **运行成本** | 决策延迟、整局耗时、Token 和费用 |
| **环境一致性** | 浏览器与无界面运行的业务结果一致性 |

对照实验包括：

- 当前快照与加入历史事件。
- 无计划与结构化计划。
- 不同事件窗口和摘要策略。
- 不同模型及预算配置。

使用多组随机种子、轮换座位和重复运行。对现有电脑玩家的信息优势单独说明；另保留使用相同玩家接口的基线，避免混淆比较条件。

**交付物：**评测报告、可复现场景、失败案例、启动文档和演示流程。

**验收标准：**能够解释主要设计的实际收益，能够复现失败，能够明确说明支持范围。

## 五、阶段衔接与完成标准

| 阶段 | 向下一阶段提供的稳定成果 |
|---|---|
| 1. 协议与基础 | 明确的数据结构、决策边界和覆盖清单 |
| 2. 游戏宿主 | 可查询、可控制、权限一致的游戏环境 |
| 3. 通信 | 可关联、可确认、可恢复连接的远程接口 |
| 4. ADK Agent | 真正由模型驱动的完整操作能力 |
| 5. 上下文 | 能持续进行长对局的局内状态管理 |
| 6. 可靠性 | 可实际使用的完整游戏体验 |
| 7. 评测交付 | 可复现、可比较、可展示的项目成果 |

**阶段 1～4 完成可玩的 Agent；阶段 5～6 完成稳定的长对局版本；阶段 7 完成可交付的项目。**

整个过程中保持三个稳定边界：**游戏规则只在游戏端，业务协议独立于模型，Session 历史独立于模型输入。** 后续更换模型、优化上下文或增加外部 Agent 接入，都围绕这些边界扩展。
